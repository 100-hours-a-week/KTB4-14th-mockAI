# AUDIGO v2 매칭 AI 설계안 — 점수 기반 추천

작성일: 2026-10-10  
범위: 빠른 BE 연동을 위한 규칙 기반 추천 API  
상태: AI 구현안. BE ↔ AI JSON 변경과 역할 분담은 연동 전 합의 필요.

## 1. 요약

AI 서버는 **내가 원하는 여행 매칭 조건과 BE가 전달한 실제 후보의 기본 프로필을 비교하고, 점수순으로 최대 3명을 반환**한다.

- 기존 AI 서버에 HTTP API 한 개와 추천 함수를 추가한다.
- 테마 일치도 80%, 여행 속도 일치도 20%로 점수를 계산한다.
- 여유롭게 ↔ 알차게 조합은 추천에서 제외한다.
- 점수 내림차순, 동점이면 닉네임 오름차순으로 정렬한다.
- 후보가 없으면 정상 응답으로 빈 목록을 반환한다.
- LLM, 임베딩, 모델 학습, 추천 전용 DB, 별도 큐를 AI 기능에 새로 도입하지 않는다.
- 성별·예산은 AI 점수에 포함하지 않는다. 성별 필터 담당과 예산 처리 정책은 BE와 먼저 확정한다.

이 기능은 학습 모델을 사용한 추천이 아니라, **AI 서버에 배치한 규칙 기반 추천**이다.

## 2. 근거와 설계 결정

피그마의 v2 최종 정의서를 기준으로 한다.

| 항목 | 정의서에서 확인한 내용 | 본 설계의 처리 |
|---|---|---|
| 기본 프로필 | 후보 노출 여부, 여행 속도, 선호 테마 최대 4개 | BE가 조회해 후보 데이터로 전달 |
| 매칭 요청 | 원하는 성별, 테마 1~3개, 여행 속도, 예산 | 첫 버전 AI는 테마·속도만 비교 |
| 속도 | 동일·인접 단계 허용, 균형 있게는 모든 단계 허용 | AI도 허용 범위를 적용 |
| 추천 | 취향 일치율 상위 최대 3명 | match_rate 순으로 반환 |
| 동점 | 닉네임 오름차순 | 동점 정렬에 nickname 사용 |
| 채팅 | 현재 두 사용자 사이 채팅방이 있으면 제외 | BE가 후보 공급 단계에서 처리 |
| 결과 재조회 | 복귀 시 같은 결과 표시 | BE가 AI 결과를 보관 |
| 백그라운드·취소·재시도 | 화면 이탈 후에도 처리, 취소, 5분 제한 등 | BE의 작업 관리 범위 |

**80:20 가중치, 반올림 방식, HTTP 계약은 정의서의 확정값이 아니라 본 설계에서 제안한 첫 구현 기준**이다.

## 3. AI와 BE의 경계

| AI 개발 범위 | BE 담당으로 합의할 범위 |
|---|---|
| 서비스 인증·요청 검증 | 사용자 인증·매칭 허용 여부 확인 |
| 후보의 테마·속도 비교 | 실제 후보 조회, 계정 활성·프로필 완성 확인 |
| 후보별 점수 계산 | 본인·현재 채팅 상대 제외 |
| 정렬 및 최대 3명 선택 | 성별 조건 필터, 예산 데이터 정책 |
| 결과 JSON 반환 | 요청 상태·취소·재시도·기한 관리 |
| 계산 시간·결과 수 로그 | 결과 보관·알림·프로필 정보 구성·채팅 연결 |

AI는 사용자 DB를 직접 조회하지 않는다. 후보 노출 동의나 현재 채팅 관계를 추측하지 않는다.

**내 요청 조건 ↔ 후보의 기본 프로필**을 비교한다. 후보가 직접 여행 매칭 요청을 만들었는지는 필요하지 않다.

## 4. 처리 흐름

1. BE가 매칭 요청과 실제 후보 목록을 준비한다.
2. BE가 AI HTTP API를 호출한다.
3. AI가 인증과 입력을 검증한다.
4. AI가 본인 후보와 허용 범위 밖의 여행 속도를 제외한다.
5. AI가 남은 후보 각각의 점수를 계산한다.
6. AI가 점수·닉네임·사용자 ID 순으로 정렬한다.
7. AI가 최대 3명을 반환한다.
8. BE가 결과를 검증·저장하고 화면에 필요한 정보를 구성한다.

AI HTTP 요청은 계산 결과를 바로 반환한다. AI 내부 job ID, 상태 조회 API, SSE, 취소 API는 이번 범위에 추가하지 않는다. FE가 화면을 떠나도 계속 처리하는 요구는 BE가 작업을 독립적으로 실행하는 방식으로 충족해야 한다.

## 5. BE ↔ AI API 계약 제안

### 엔드포인트

`POST /api/ai/v1/matches/candidates`

헤더:
- `Content-Type: application/json`
- `Authorization: Bearer <서비스 간 토큰>`

기존 AI 서버 인증 방식을 재사용한다. 사용자 로그인 토큰이 아니라 BE ↔ AI 서비스 인증이다.

### 요청

```json
{
  "matching_request_id": 10,
  "user_id": 1,
  "theme": ["NATURE", "FOOD"],
  "pace": "RELAXED",
  "candidates": [
    {
      "user_id": 21,
      "nickname": "나나",
      "theme": ["NATURE", "FOOD", "REST"],
      "pace": "RELAXED"
    },
    {
      "user_id": 35,
      "nickname": "다다",
      "theme": ["NATURE", "CULTURE"],
      "pace": "BALANCED"
    }
  ],
  "limit": 3
}
```

| 필드 | 규칙 |
|---|---|
| matching_request_id | 양의 정수, BE 요청과 결과 연결용 |
| user_id | 양의 정수, 요청자 ID |
| theme | 요청자가 이번에 원하는 테마 1~3개, 중복 불가 |
| pace | 요청자가 이번에 원하는 여행 속도 |
| candidates | 실제 후보 목록. 빈 목록 허용 |
| candidates[].user_id | 양의 정수, 후보 간 ID 중복 불가 |
| candidates[].nickname | 비어 있지 않은 문자열. 동점 정렬용 |
| candidates[].theme | 후보 기본 프로필의 테마 1~4개, 중복 불가 |
| candidates[].pace | 후보 기본 프로필의 여행 속도 |
| limit | 기본 3, 정수 1~3 |

테마 enum: NATURE, FOOD, CULTURE, REST, SNS, ACTIVITY  
속도 enum: RELAXED, BALANCED, PACKED

후보 목록의 전달 상한은 BE와 합의하고 설정값으로 둔다. 상한을 초과하면 잘라서 평가하지 않고 입력 오류로 반환한다. BE가 후보를 먼저 추린다면 조회 순서대로 임의 제한하지 않고 관련성 있는 후보를 공급해야 한다.

후보 전체 프로필 문서나 이미지 URL은 필요하지 않다.

### 성공 응답

```json
{
  "matching_request_id": 10,
  "ranking_version": "theme-pace-v1",
  "candidates": [
    {
      "user_id": 21,
      "match_rate": 100
    },
    {
      "user_id": 35,
      "match_rate": 50
    }
  ],
  "count": 2
}
```

- HTTP 200, 평평한 JSON으로 반환한다. FE용 message/data 래퍼를 AI가 만들지 않는다.
- 후보 사용자 ID는 요청에서 받은 목록에 존재해야 한다.
- match_rate는 정수 0~100이다.
- count는 실제 반환 목록 길이와 같다.
- ranking_version은 계산 기준 식별용이며 첫 버전에서 고정한다.
- 후보 수가 limit보다 적으면 존재하는 후보만 반환한다.

### 후보 없음

```json
{
  "matching_request_id": 10,
  "ranking_version": "theme-pace-v1",
  "candidates": [],
  "count": 0
}
```

HTTP 200으로 처리한다. 후보 없음은 서버 오류가 아니다.

### 현재 BE 코드와의 차이

확인했던 BE 커밋 `675edb742cad70ebcb223ff38aa9332c8c7782ff` 기준:
- 요청에는 내 조건만 있고 후보 목록과 limit이 없다.
- 응답 후보에는 nickname, profile_image_url, theme, pace, match_rate를 기대한다.

따라서 본 설계는 **현재 계약 그대로 연결되는 구현이 아니다.** BE 요청 DTO에 candidates·limit을 추가하고, AI 응답은 사용자 ID·점수 중심으로 받도록 응답 DTO와 정보 구성 로직을 변경하는 합의가 필요하다. BE는 공급한 후보 데이터와 사용자 정보로 카드 정보를 구성한다.

## 6. 점수 계산

### 6.1 속도 허용 범위

| 요청 속도 | 후보 속도 | 처리 | 속도 점수 P |
|---|---|---|---:|
| RELAXED | RELAXED | 추천 가능 | 1 |
| RELAXED | BALANCED | 추천 가능 | 0.5 |
| RELAXED | PACKED | 제외 | — |
| BALANCED | RELAXED | 추천 가능 | 0.5 |
| BALANCED | BALANCED | 추천 가능 | 1 |
| BALANCED | PACKED | 추천 가능 | 0.5 |
| PACKED | RELAXED | 제외 | — |
| PACKED | BALANCED | 추천 가능 | 0.5 |
| PACKED | PACKED | 추천 가능 | 1 |

### 6.2 테마 점수

`T = 요청 테마와 후보 테마의 교집합 개수 / 요청 테마 개수`

후보가 추가 테마를 가지고 있다는 이유로 감점하지 않는다. 요청자의 이번 조건을 얼마나 충족하는지 계산한다.

### 6.3 최종 점수

`match_rate = floor(100 × (0.8 × T + 0.2 × P) + 0.5)`

0~100의 정수로 반올림한다. Python 내장 round의 짝수 반올림과 혼동하지 않도록 위 규칙을 명시한다.

정렬:
1. 반환할 정수 match_rate 내림차순
2. nickname 오름차순
3. nickname도 같으면 user_id 오름차순

첫 구현은 Python 문자열 비교 기준을 제안한다. 한국어·영문·숫자 혼합 닉네임의 정렬은 DB collation과 다를 수 있으므로 BE와 같은 기준을 사용하도록 합의한다.

최소 추천 점수는 이번 버전에 두지 않는다. 필수 조건을 충족한 후보는 테마가 겹치지 않아도 점수 계산 대상이다. 임의로 낮은 점수 후보를 제외하지 않는다.

### 6.4 계산 예시

요청: 자연·미식 / 여유롭게

| 후보 | 프로필 | T | P | 점수 |
|---|---|---:|---:|---:|
| A | 자연·미식·휴식 / 여유롭게 | 1 | 1 | 100 |
| B | 자연·미식 / 균형 있게 | 1 | 0.5 | 90 |
| C | 자연·문화 / 여유롭게 | 0.5 | 1 | 60 |
| D | 미식·SNS / 균형 있게 | 0.5 | 0.5 | 50 |
| E | 자연·미식 / 알차게 | — | — | 제외 |

결과: A → B → C.

점수는 규칙에 따른 취향 유사도이다. 실제 여행 성공 확률이나 검증된 만족도는 아니다.

## 7. 코드 구성

기존 AI 프로젝트 구조에 맞춰 아래 역할만 추가한다.

| 구성 | 책임 |
|---|---|
| matching API | 인증·스키마 검증 후 서비스 호출, 응답 반환 |
| matching schemas | 요청·후보·응답 모델 정의 |
| matching service | 본인 제외·속도 조건·정렬·상위 limit 선택 |
| matching scoring | 테마·속도 점수와 최종 점수 계산 |
| matching tests | 규칙과 API 계약 검증 |

핵심 함수 형태:

```python
recommend(
    request_conditions,
    candidates,
    limit=3,
) -> recommendation_result
```

점수 함수는 HTTP나 DB에 의존하지 않는 순수 함수로 구현한다. 기존 AI 서버에 경로를 추가하며 별도 추천 서버를 만들지 않는다.

## 8. 오류·운영 처리

| 상황 | AI 처리 |
|---|---|
| 후보 목록 비어 있음 | 200, 빈 결과 |
| 속도 필터 후 모두 제외 | 200, 빈 결과 |
| 자기 자신만 후보로 전달됨 | 제외 후 200, 빈 결과 |
| 잘못된 enum·테마 개수·limit·중복 ID | 422, 입력 오류 |
| 인증 토큰 누락·불일치 | 기존 인증 규약 적용, 기본 제안 401 |
| 예상하지 못한 내부 오류 | 500, 내부 오류 |

입력 오류를 일부 후보만 조용히 무시하는 방식으로 처리하지 않는다. 표준 오류 응답은 기존 AI 서버 형식을 재사용한다.

AI 내부에서 HTTP 호출 재시도를 하지 않는다. BE가 필요 시 같은 요청을 다시 호출할 수 있고, 같은 입력·계산 버전에는 같은 결과를 반환한다. AI가 상태를 저장하지 않으므로 중복 요청이 결과 저장·알림을 중복 생성하는 문제는 BE가 관리한다.

로그는 요청 ID, 입력 후보 수, 반환 후보 수, 처리 시간, 계산 버전, 오류 종류만 우선 기록한다. 토큰과 전체 후보 개인정보를 로그에 남기지 않는다.

## 9. 최소 검증 항목

1. 테마 모두 일치·속도 동일이면 100점.
2. 테마 모두 일치·속도 인접이면 90점.
3. 요청 2개 중 1개 일치·속도 동일이면 60점.
4. 여유롭게 ↔ 알차게 후보는 제외.
5. 균형 있게 요청은 세 속도 모두 허용.
6. 후보의 추가 테마 때문에 점수가 낮아지지 않음.
7. 점수 동점은 닉네임순, 닉네임도 같으면 ID순.
8. 본인은 제외하고 최대 limit명만 반환.
9. 빈 목록·필터 후 빈 결과는 200.
10. enum·테마 중복·후보 ID 중복·limit 오류는 입력 오류.
11. count와 실제 목록 길이가 일치하고 같은 입력은 같은 결과.
12. BE 실제 호출에서 인증·JSON 파싱·카드 정보 구성 확인.

응답 속도는 테스트 후보 수와 서버 사양을 함께 기록해 측정한다. 측정하지 않은 지연시간 목표나 처리량을 보장하지 않는다.

## 10. 개발 순서와 연동 전 합의

### 개발 순서

1. BE와 아래 계약을 확정한다.
2. 테스트 후보로 순수 점수·추천 함수를 구현한다.
3. 기존 AI HTTP API에 경로·스키마·인증을 연결한다.
4. 최소 규칙·계약 검증을 실행한다.
5. BE가 실제 후보를 전달해 end-to-end 연동을 확인한다.

### 합의가 필요한 항목

- BE가 후보 목록을 공급하고 AI가 DB를 직접 조회하지 않는가?
- 요청·응답 JSON을 본 설계로 변경할 수 있는가?
- 빠른 연동을 위해 HTTP를 사용할 것인가? 큐가 필수라면 같은 추천 함수를 호출하는 어댑터로 연결한다.
