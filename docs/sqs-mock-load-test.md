# SQS Mock Worker 부하 테스트

이 문서는 현재 저장소(`KTB4-14th-mockAI`)의 AI 서비스에 적용됩니다.
기존 HTTP Mock 경로는 변경하지 않습니다. SQS 테스트를 위해 BE에 새로운
`/mock` API를 만들거나 FE를 재배포할 필요는 없습니다.

## 적용 범위

BE는 기존처럼 `POST /api/v2/travel-plans` 요청을 접수하고 Outbox를 기록합니다.
이 Worker는 실제 테스트용 Job 큐에서 요청을 받고, 진행 상태와 최종 결과를 실제
테스트용 Result 큐로 보냅니다. 외부 AI·카카오를 호출하는 생성 부분만 Mock으로 대체합니다.
이 코드가 큐, IAM 정책, DB 스키마, 배포 환경변수나 운영 설정을 자동으로 만들거나
변경하지는 않습니다.

Mock은 기존 생성 파이프라인에 가짜 의존성을 넣어 재사용합니다. 결과는 여행 일시와
여행 ID 등 요청에 따라 생성되며, 모든 요청에 같은 일정을 그대로 반환하지 않습니다.
메시지 공통 필드와 최종 결과는 기존 BE 계약을 유지합니다. 프로세스 메모리 기반 중복
처리 방지와 결과 발행 재시도 정책도 유지하므로, 재시작 이후까지 정확히 한 번만
처리되는 것을 보장하는 Worker는 아닙니다.

## 배포할 테스트 AI 서비스 설정

```dotenv
AWS_REGION=ap-northeast-2
AUDIGO_AI_JOB_QUEUE_URL=<테스트 전용 Job 큐 URL>
AUDIGO_AI_RESULT_QUEUE_URL=<테스트 전용 Result 큐 URL>
AUDIGO_AI_QUEUE_WORKER_MODE=mock
AUDIGO_AI_QUEUE_WORKER_CONCURRENCY=1
MOCK_JOB_DELAY_SECONDS=30
MOCK_SCENARIO=success
```

- `live`는 기존 동작과 호환되는 기본값이며 실제 AI·카카오 의존성을 사용합니다.
- `mock`은 Mock 생성기를 선택합니다. 이 모드의 큐 작업에는 OpenAI·카카오 키가
  필요하지 않지만, 실제 SQS를 사용하므로 AWS 인증과 기존 수신·발행·삭제 권한은 필요합니다.
- `off`는 두 큐 URL이 있어도 이 서비스가 SQS 클라이언트를 생성하거나 큐를 소비하지
  않게 합니다. HTTP API는 계속 사용할 수 있습니다.
- 동시 처리 수는 **애플리케이션 프로세스당** 1~32의 정수입니다. 프로세스나 복제본이
  여러 개면 전체 동시 처리 수는 그만큼 늘어납니다. 처음에는 1로 시작하고, 실험마다
  하나의 설정만 변경하세요.
- 정상 Mock 작업은 생성 시작부터 최종 완료까지 최소 설정 시간만큼 걸립니다.
  진행 상태를 먼저 발행하고, 남은 시간은 이벤트 루프를 막지 않고 기다립니다.
  단계별 지연이나 SQS 전달 지연 설정이 아니며, 전체 응답 시간을 정확히 30초로
  보장하는 것도 아닙니다. 생성 연산·발행·스케줄링·큐 대기·BE 저장 시간 때문에 더 걸릴 수 있습니다.
- 지연 0초도 지원합니다. 음수·무한대·NaN은 거부하며, Mock 모드에서는 생성 제한
  시간(현재 300초)보다 작아야 합니다.
- `MOCK_SCENARIO`는 `fail_place`, `fail_stay`, `fail_route`, `unavailable`, `drop`도
  지원합니다. 이 경우 기존 계약에 맞는 최종 `FAILED`를 발행하며, 정상 작업용 지연을
  기다리지 않습니다. `drop`도 Result 무응답을 뜻하지 않습니다. Worker가 최종 일정
  누락을 감지해 실패 메시지를 발행합니다.
- `MOCK_STAGE_DELAY_SECONDS`는 기존 HTTP 전용 설정입니다. SQS 작업 지연에 추가되지 않습니다.
- 이 변경이 포함된 이미지로 **배포할 테스트 AI 서비스**에 환경변수를 적용하고
  재시작·재배포해야 합니다. 로컬 k6 셸에 설정해도 서버 Worker는 바뀌지 않습니다.

## 시작 전 소비자 분리

테스트 전용 Job·Result 큐를 준비하고, 테스트 BE와 이 Worker가 같은 큐 쌍을 사용하도록
하는 구성을 권장합니다. 다른 환경과 DB는 분리하세요. 별도 로컬 DB를 사용하는 BE를
공유 staging Result 큐에 연결하면 안 됩니다.

기존 staging 큐를 재사용해야 한다면 테스트 전용 시간대를 협의하고, 해당 Job 큐를
소비하는 모든 실제 AI Worker를 중지한 뒤 진행 중인 작업을 확인해야 합니다.
이 서비스의 모드 설정은 다른 저장소·프로세스·배포의 Worker를 중지하지 않습니다.
SQS 메시지는 HTTP의 `/mock` 경로를 선택하지 않으며, 각 소비자가 메시지 복사본을
하나씩 받는 구조도 아닙니다.

같은 큐에 실제 Worker와 Mock Worker를 동시에 연결한 뒤, 수신한 메시지를 구분해서
버리는 방식은 사용하지 마세요. `queue_worker_started` 로그에서 `mode=mock`과
의도한 동시 처리 수를 확인하세요. 공유 소비자나 큐 설정 변경은 클라우드 담당자와
먼저 조율해야 합니다.

## 실행 및 관측

1. staging 테스트 계정 토큰을 갱신하고, 인증이 필요한 조회 요청이 성공하는지 확인합니다.
2. BE의 SQS 활성화와 테스트 Job 큐 발행 설정을 확인합니다.
3. v2 생성 요청을 1건 보냅니다. 응답의 생성 작업 ID로 진행 상태, 최종 `COMPLETED`,
   저장된 일정을 확인합니다. HTTP 202는 완료가 아니라 접수 성공입니다.
4. 배포된 Mock을 확인한 뒤 기존 BE P-01 스크립트에 `CONFIRM_AI_MOCK=true`와
   `P01_CREATION_PATH=/api/v2/travel-plans`를 사용할 수 있습니다. 이 플래그 자체가
   Worker를 설정하지는 않습니다. Git Bash에서 Windows용 k6를 실행할 때는
   `MSYS2_ARG_CONV_EXCL='*'`로 API 경로 인자의 자동 변환을 방지합니다.
5. 서로 다른 계정의 동시 요청을 단계적으로 늘립니다. 지연 30초·동시 처리 1개라면
   오버헤드를 제외해도 약 30초당 1건이 최대 정상 생성 처리량입니다. 유입량이 이를
   넘으면 Job 큐가 쌓이는 것은 예상되는 동작입니다. BE 결과 처리 능력을 측정할 때는
   Worker 동시 처리 수를 별도 실험으로 조절합니다.
6. 고유 완료·실패·미완료 작업 수, 결과 메시지 처리량, 큐 대기 시간·적체, BE CPU·GC·
   Hikari와 DB 지표를 기록합니다. k6의 HTTP 시간은 큐 대기나 JSON 파싱 시간이 아니므로,
   구간별 애플리케이션 계측은 별도로 필요합니다.

Visibility timeout은 의도한 메시지 처리 시간보다 길게 설정하고 재전달도 관측하세요.
이번 변경에는 visibility 연장 기능이 없습니다. 실패 반복, 자원 고갈, 설명되지 않는
미완료 작업이 발생하면 부하를 더 늘리지 마세요. k6를 중지해도 이미 접수된 작업은
취소되지 않으므로, 처리가 끝날 때까지 관측하고 모든 작업 ID의 최종 상태를 대조해야 합니다.

## 테스트 종료 및 원복

새 요청 유입을 중단하고, 접수된 작업의 처리 완료와 실패 내역을 확인합니다.
공유 큐의 별도 실제 AI Worker를 다시 켜기 전에는 이 서비스를 `off`로 재배포하세요.
이 서비스 자체를 실제 생성 소비자로 사용할 계획이라면 `live`로 전환합니다.
이 과정에서 공유 큐를 비우거나 DB 작업 상태를 직접 덮어쓰지 않습니다.

기본 설정은 기존 실제 AI 모드와 순차 처리를 유지합니다. 의존성·메시지 버전·API 버전은
변경하지 않습니다. 이번 기능을 한 PR로 묶고, 필요할 때 한 커밋으로 되돌릴 수 있도록
GitHub에서 머지 시 `Squash and merge`를 선택합니다. 환경변수 변경은 Git 커밋과
별개이므로, 코드를 되돌릴 때 배포 설정도 함께 확인해야 합니다.


프로세스 내 중복 방지, 취소·스트림 정리를 검증합니다. 실제 AWS 배포·IAM·visibility
설정이나 BE의 DB 저장까지 검증하는 것은 아닙니다.
